# AA Manager — an account-abstraction custody contract for Midnight

A Compact contract that holds value on behalf of registered accounts and attributes every unit of
it to exactly one **(account, colour)** pair, where a colour is a token identifier. The contract is
deliberately **open**: it has no token registry, no admin circuit and no colour list anywhere. It
deploys knowing zero colours and custodies whatever arrives — including a token minted long after
it was deployed.

Two things make it *account abstraction* rather than a plain vault:

- **Dual-mode authorization.** An account is either **native** — authorized by a Midnight witness
  secret whose commitment *is* the account id — or **EVM** — authorized by an Ethereum EOA signing
  an EIP-712 payload. The mode is fixed at registration and the two paths are explicitly isolated.
  An Ethereum key can therefore custody and move value on Midnight without ever holding a Midnight
  key.
- **One write gateway.** Every state-changing authorized action goes through a single circuit,
  `execute`, taking a fixed-width action envelope plus an ECDSA signature. A `selector` field picks
  the action:

  | selector | action | | selector | action |
  |---:|---|---|---:|---|
  | 0 | register a native account | | 4 | internal transfer, shielded |
  | 1 | register an EVM account | | 5 | internal transfer, unshielded |
  | 2 | withdraw shielded | | 6 | open a swap-maker offer |
  | 3 | withdraw unshielded | | | |

  Every field a selector does not use is constrained to its canonical zero form *before* any
  authentication or custody logic runs. Deposits are separate entry points (`depositShielded`,
  `depositUnshielded`): they only ever credit, so they need no gateway.

Value is **family-separated**: shielded value (zswap coins pooled inside the contract) and
unshielded value (the contract's own kernel balance) live in separate maps under distinct key
domains, so a shielded and an unshielded colour with byte-identical identifiers can never alias.

Two facts about the compiled contract are load-bearing and connected: **`execute` fits in a k=19
circuit** (382,781 of 524,288 rows) and **the contract emits no events**. See
[Why k=19 matters](#why-k19-matters).

The authoritative description is the header of
[`contracts/manager.compact`](contracts/manager.compact) — it documents the safety story guard by
guard, the storage invariants, and which byte constants are frozen. Read that before changing
anything.

```

  test-support/
    minter.compact         a token source, used only by tests: a per-deployment constructor tag
    minter-collide.compact becomes two contract-scoped colours (minter-collide is the inverse
                           fixture — one separator feeding both families, so its two colours are
                           byte-EQUAL, which is how family separation is proven to be real)

tests/
  package.json             the test runtime: pinned deps, FROZEN lockfile
  pnpm-lock.yaml
  tsconfig.json
  lib/                     shared by both tiers — EIP-712 codec, semantic-commitment recipe, secp
                           helpers, the in-process circuit simulator (sim.ts), the refusal-matrix
                           harness, and the committed AuthCodec mirror contract with its compiled
                           artifacts
  fixtures/                frozen known-answer tests: the EIP-712 fixture set and its deterministic
                           generator, the byte contract it implements, the spec's 18-row
                           step-ledger table, and the two gate baselines (refusal matrix, artifact)
  simulation/              KEYLESS suites — this is the tier CI runs
  integration/             node-stack suites — on demand only (currently empty; see its README)
  generated/               compiler output. Gitignored, regenerated by scripts/compile.sh

scripts/
  toolchain.sh             THE toolchain pin: obtains the compiler image and verifies it. Sourced by
                           the four scripts below; run directly, it is CI's toolchain step
  compile.sh               compile the contracts with the pinned toolchain
  measure-k.sh             report a circuit's k and constraint-row count
  check-artifact.sh        the artifact gate: rows, k and the generated surface vs the baseline
  keygen.sh                generate proving/verifying keys (expensive — read its header)
  verify-loader.sh         prove the generated key can actually be loaded
  test-sim.sh              run the simulation tier
  test-integration.sh      bring up the local stack, run the integration tier, tear it down

docker/
  compactc.Dockerfile      the pinned Compact toolchain, and the provenance record for every
                           artifact in this repository
  compose.yml              the local Midnight stack (node + indexer + proof server), pinned by
                           digest, used only by the integration tier

.github/workflows/ci.yml   on every push and PR: verify the toolchain, compile, run the artifact
                           gate, run the simulation tier
REMOVALS.md                what this repository used to contain, and where it went
```

Every script is self-documented: its header says what it does, what it needs, and why it is built
the way it is. `--help` is not implemented on purpose — read the top of the file.

## Test tiers

| | simulation | integration |
|---|---|---|
| what it does | executes circuits directly in the Compact runtime's simulator | drives the contract through a real node, indexer and proof server |
| needs | Docker + the toolchain image | Docker + the stack images + a proving key |
| keys / proofs / network | **none** | all three |
| runtime | ~12 s | minutes, plus key generation |
| runs in CI | **yes, every push** | no |
| command | `scripts/test-sim.sh` | `scripts/test-integration.sh` |

```sh
scripts/test-sim.sh            # compiles, then runs 359 tests across 13 files
scripts/test-sim.sh --skip-compile
scripts/test-sim.sh --reinstall   # after a lockfile change: rebuild the scratch volume's deps
```

By default the suite runs inside the pinned Node image in a scratch Docker volume, so a shared host
needs no local Node and nothing is written into your working tree. `AA_TEST_RUNTIME=native` runs it
directly on the host instead — that is what CI uses, since a CI runner is already isolated.
Dependencies are always installed with `pnpm install --frozen-lockfile`; the lockfile is never
updated by a test run.

The simulation tier asserts its own keylessness: it fails if any `*.prover` or `*.verifier` file
exists in the test tree, both on the host before it starts and inside the container before vitest
runs. (The scan skips `node_modules`, because one pinned dependency ships key fixtures of its own.)

**Two gates run beside the tier**, and both are in CI:

| gate | command | what it proves |
|---|---|---|
| refusal matrix | part of the tier (`simulation/refusal-matrix.test.ts`, 207 of the 359 tests) | every `assert` string in the Compact sources is reached by a test and refuses with the exact expected message, leaving the ledger untouched. Its coverage claim is mechanical: it reads the assert strings back out of `contracts/**/*.compact` at test time rather than from a hand-maintained list, which is why the Docker runtime stages `contracts/` read-only into the run volume. |
| artifact gate | `scripts/check-artifact.sh` | the compiled Manager is still the same artifact: per-circuit `k` and exact row count for all nine proof-bearing circuits, the sorted `name:pure:proof` circuit list, the set of emitted `.zkir` files, and the generated `Ledger` fields / `Witnesses` keys / exported struct names — all against `tests/fixtures/00014-artifact-baseline.json`. It also records the compiler, language and runtime versions, the image ref and the SHA-256 of the two compiler binaries (`compactc.bin`, `zkir-v3`) — the same hashes `scripts/toolchain.sh` verifies, and reproducible where an image ID is not — so a toolchain change shows up as a visible provenance note next to numbers that either did or did not move, while a rebuilt image of the same pinned archive reports none. `--write-baseline` re-records it after an intentional change; it never runs by accident. |

**The k=20 reference oracle.** Twenty of these tests are differential: they load the current
Manager *and* the last pre-v5 Manager in one process, and require byte-equal EIP-712 output, ledger
state, zswap structure and refusal text. That older Manager is a frozen reference, not a second
product, so it is not in the tree — `scripts/compile.sh` reads it out of this repository's history
at a pinned commit, checks its SHA-256, and compiles it. This means **a shallow clone cannot run
the full tier**: use `git fetch --unshallow`, or `fetch-depth: 0` in CI.

## Toolchain provenance

Every artifact here — the nine ZKIRs, the measured k, the proving keys — is the output of one
pinned compiler: **Compact compiler 0.34.0, language 0.26.0, Compact runtime 0.19.0**, the official
toolchain for Midnight **ledger 9**.

**The pin of record is the release archive, not an image.** `docker/compactc.Dockerfile` fetches

```
release  compactc-v0.34.0            (LFDT-Minokawa/compact, published 2026-08-25)
asset    compactc_v0.34.0_aarch64-unknown-linux-musl.zip
sha256   d3e292c4f48e257dcd6b3d3e3e4743d7d8ea0729f48953eab91a366d44cd026d
```

and verifies that SHA-256 with `sha256sum -c` during the build, so the build cannot silently drift
and any host can reproduce the toolchain from the published release. That matters because the
previous design pinned images that turned out to be unobtainable: the scripts pinned a **local** tag
no registry can serve, and the published GHCR copy returned "not found", so everything had already
been falling through to a Dockerfile build without saying so.

**One file obtains it: [`scripts/toolchain.sh`](scripts/toolchain.sh).** `compile.sh`,
`measure-k.sh`, `keygen.sh` and `check-artifact.sh` source it, and CI executes it, so CI and a
laptop run identical code. Its `ensure_image`:

1. uses `$COMPACTC_IMAGE` (default `aa-compactc:0.34.0`) if that image is already local;
2. else pulls `$COMPACTC_PUBLISHED_IMAGE` and tags it — that variable is **empty by default**,
   because nothing is published; set it to a digest to use a published image as a cache;
3. else builds `docker/compactc.Dockerfile`.

Then, **on every path**, it proves what arrived and exits 70 on any mismatch:

```
compactc --version           0.34.0
compactc --language-version  0.26.0
/opt/compactc/compactc.bin   sha256 628b343f9b0ebe32e6e6a141b6f73cc66edb19c516a4817b478c3b47f74230d5
/opt/compactc/zkir-v3        sha256 6a91308419d24bc0633210897d10c7c1b2193444e8bde09ce763e9556cb8f93a
```

The binary hashes are the identity check rather than the image ID for a concrete reason: rebuilding
the same Dockerfile produces a **different image ID** from **identical binaries**. The binaries are
what decide every ZKIR byte and every key, so they are what gets verified. Set `COMPACTC_IMAGE=<ref>`
to point the scripts at another build.

The image is **arm64/linux**: the pinned release asset is `aarch64-unknown-linux-musl`, so the
compiler binary runs on arm64 only. CI therefore runs on an ARM runner. Upstream publishes an
`x86_64` asset from the same release; using it means changing both the URL and the SHA-256 in
[`docker/compactc.Dockerfile`](docker/compactc.Dockerfile), which is a deliberate re-pin and would
need its own verification that the outputs match.

Transport moved once and identity did not: upstream relocated from `midnightntwrk/compact` to
`LFDT-Minokawa/compact`, and the old release URLs now return 404 — which is why the URL in the
Dockerfile changed during the 0.33.0 era. Everything since is served from the LFDT-Minokawa release
pages.

### History: compiler 0.33.0 (superseded 2026-09-03)

The repository was pinned to **compiler 0.33.0 / language 0.25.0 / runtime 0.18.0-rc.1** from
release `compactc-v0.33.0-rc.2`, asset `compactc_v0.33.0-rc.2_aarch64-unknown-linux-musl.zip`,
archive sha256 `3aa23812b0b086dbce07da3931a40dcb01bec9676b1ceed7f2d0be370ab2dc46`; the rebuilt
toolchain's binaries hash to `compactc.bin`
`2abdacfddf1b8ccc85ce6f4317b7a75b9f53641de6df0f387f86819084d10947` and `zkir-v3`
`75153f473f8d1920fcbfc6c207e1038c9049bd0f17ae88c81367cd08c3522176`. That archive is still on the
release page, so 0.33.0 remains reproducible if an older artifact ever has to be rebuilt. The
scripts also used to pin `aa00006-compactc@sha256:f57ca2d8…` and CI
`ghcr.io/acedward/aa-compactc:0.33.0` — the unobtainable pair described above.

**What the 0.33.0 → 0.34.0 move actually changed.** No Compact source needed an edit — every source
already imports `CompactStandardLibrary` wholesale, which is exactly the import that now supplies
`Secp256k1Point` and the other types that stopped being built-ins — and **all nine ZKIRs came out
byte-identical**, so every row count and every `k` is unchanged and the generated `index.d.ts` is
the same file. What did change is the runtime: generated code now calls
`checkRuntimeVersion('0.19.0')` and will not load on 0.18.0-rc.1. The frozen EIP-712 fixture set
regenerates byte-identically apart from its own provenance label.

## Why k=19 matters

`k` is the log2 of a circuit's constraint domain, and it decides the **proving key size**. It is not
a performance nicety here — it is a hard product requirement, because Node's `fs.readFile` cannot
return more than 2 GiB in one Buffer and the pinned midnight-js loader reads a prover key exactly
that way:

```
RangeError [ERR_FS_FILE_TOO_LARGE]: File size (2282126073) is greater than 2 GiB
```

2,282,126,073 bytes is what `execute.prover` weighed at k=20. At k=19 the same key is
**1,141,041,759 bytes** — 53.1% of the ceiling — and it loads. Measure it yourself:

```sh
scripts/compile.sh manager
scripts/measure-k.sh execute        # -> Mock compiling circuit "execute.zkir" (k=19, rows=382781)
```

382,781 rows is 141,507 (27.0%) under the 2^19 = 524,288 ceiling. `measure-k.sh` runs
`zkir-v3 mock-compile`: it reports (k, rows) and writes a throwaway `.bzkir`, and it never
generates a key.

### The nine proof-bearing circuits

`contract-info.json` lists 19 circuits — nine proof-bearing, nine pure, and `myAccount`, which is
impure yet emits no key. Only the nine below cost a proving key, and the artifact gate measures
every one of them, because `execute`'s 27% of headroom says nothing about the thin ones:
`depositUnshielded` sits **274 rows (3.3%)** under its own ceiling.

| circuit | k | rows | headroom under 2^k |
|---|---|---|---|
| `execute` | 19 | 382,781 | 141,507 (27.0%) |
| `depositShielded` | 16 | 42,239 | 23,297 (35.6%) |
| `depositUnshielded` | 13 | 7,918 | **274 (3.3%)** |
| `shieldedAccountBalance` | 13 | 4,001 | 4,191 (51.2%) |
| `unshieldedAccountBalance` | 13 | 4,001 | 4,191 (51.2%) |
| `accountRecord` | 9 | 316 | 196 (38.3%) |
| `poolValue` | 8 | 159 | 97 (37.9%) |
| `isRegistered` | 8 | 129 | 127 (49.6%) |
| `poolHasColour` | 8 | 129 | 127 (49.6%) |

Total 441,673 rows. These numbers are **identical on compilers 0.33.0 and 0.34.0** — the nine ZKIRs
came out byte-identical across the bump — and they are the numbers
`tests/fixtures/00014-artifact-baseline.json` pins.

**This is also why the contract emits no events.** Computing and emitting a semantic commitment for
each action inside the circuit cost roughly 367,000 rows — about 38% of `execute` — dominated not
by hashing but by *serializing* the 1,024-byte action envelope into keccak preimages. So the proved
call transcript is the authority instead, and the recipe stays available as the exported **pure**
circuit `semanticCommitmentFor`, which anyone can run off-chain against the compiled artifact. No
consumer may trust a commitment it did not recompute.

## Key regeneration

You need keys only to **prove** or **deploy**. Tests and CI never touch one.

```sh
scripts/keygen.sh          # ~155 s at ~2.1 GiB peak on 4 CPU / 20 GiB; writes ~1.2 GB
scripts/verify-loader.sh   # confirms the prover key reads through the pinned Node loader
```

Regenerate whenever a change to `contracts/manager.compact` changes any `.zkir`. Comment-only edits
do not; changing a domain-separator string does. A compiler bump *may*: the 0.33.0 → 0.34.0 move did
not, because it left all nine ZKIRs byte-identical.

**The SRS is the one thing that needs the network.** Unlike compilation and measurement, key
generation needs the universal KZG structured reference string `bls_midnight_2p<k>` for every
distinct circuit `k` — on a cold cache `zkir` fetches it from `https://srs.midnight.network/`, so
key generation cannot run in an offline container without it. The convention here is **fetched
once, hash-pinned, reused, never silently re-fetched**: put the files in `tests/generated/zk-params/`
and `scripts/keygen.sh` mounts them via `MIDNIGHT_PP` and keeps the generation container itself
offline. This contract needs five, totalling **114,968,468 bytes**:

```
bls_midnight_2p8   bls_midnight_2p9   bls_midnight_2p13   bls_midnight_2p16   bls_midnight_2p19
```

The tool verifies each file against its own built-in expected hash, so a substituted parameter file
is rejected by the compiler itself, not merely by bookkeeping. Without that directory
`scripts/keygen.sh` refuses rather than quietly opening the network; pass `--allow-network` to fetch
once, then keep the directory.

Keys and SRS files are gitignored and are never committed.

## Continuous integration

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on every push and pull request:

1. obtain and verify the pinned toolchain with `scripts/toolchain.sh` — the same code a laptop runs,
2. compile the contracts,
3. run the **artifact gate** (`scripts/check-artifact.sh --skip-compile`: all nine circuits' rows
   and `k`, plus the generated surface), and
4. run the **simulation tier**, refusal matrix included.

No node stack, no proof server, no keys, no SRS, and **no secrets**: with nothing published, the
toolchain is built from the SHA-256-pinned release archive, and the GHCR login step only runs if
`COMPACTC_PUBLISHED_IMAGE` is set to a published cache. The job runs on `ubuntu-24.04-arm` because
the compiler binary is arm64-only, and checks out with `fetch-depth: 0` because the k=20 reference
oracle lives in this repository's history.

## Notation in the comments

Comments throughout the contract and the suites cite requirement codes (`FR-2xx`, `FR-3xx`),
negative-case codes (`NC-x`) and probe names (`P-COLL`). These are identifiers from the design
documents this contract was built against; they are stable labels for "this specific requirement",
and each is stated in full where it is used, so no comment depends on reading a document that is
not here.
